# 项目总结

> 起于「有没有比 ProcessOn 更好的 AI 流程图工具」，终于「在 ProcessOn 现有画布上做 AI 增量改图」的两套可用方案。
> 本文档记录**结论、证据、踩过的坑**，供后续维护者接手。

---

## 一、问题是什么

原始需求：团队一起画流程图，想要 AI 深度参与（人机协同），又要像 ProcessOn 那样多人实时操作同一张画布。

考察过 ProcessOn 之外的工具后，结论是：**换工具的成本远高于在原工具上增强**。
于是目标变成 —— 保留 ProcessOn，让 AI 能在现有画布上做精确的增量修改。

关键约束：目标为需要多人协作的团队场景，可能存在受限网络或私有化部署要求。

---

## 二、结论

**能改。而且不用官方 API。**

ProcessOn 前端把文档模型挂在 `window.Model` 上，写入走 `window.MessageSource`。
往页面注入一段 8KB 的桥接层，就能读结构、增删改图元，改动走协同通道实时同步给同事。

### 两套实现，按 AI 工具选

| | DSH 方案 | WorkBuddy 方案 |
|---|---|---|
| 执行者 | AI 通过浏览器扩展控制你正开着的标签页 | AI 用 Playwright 自带的 Chromium |
| 要装什么 | DSH + 浏览器扩展 + 技能 | Node + Chromium + 技能 |
| 占用你的浏览器 | 是（会切换标签页） | 否 |
| 认证 | 复用登录态 | URL 里的 `encrypted_session` |
| 单次读图 | 6–30 ms | 约 3–5 s |
| 落库校验 | 无 | 有 |
| 无人值守 | 不行 | 可以 |
| kdocs 内嵌图 | 支持 | 不支持 |

两套共用同一份桥接层，改的是同一份文档，互不冲突。

> 完整对比（实测数据、失败模式、选型决策树、改进优先级）见 [`docs/两方案对比.md`](两方案对比.md)。

### 交付物

- `dsh/skill/dsh-processon-diagram-editor/` — DSH 技能（自包含，含测试）
- `wb/` — WorkBuddy 的 CLI 与技能运行时
- `dist/ProcessOn流程图AI助手.zip` — 给同事的成品包（约 400 KB，43 个文件）

## 三、技术核心：四个必须知道的坑

这四条都是实测撞出来的，不知道就会「数据变了但画布不动」或者「图元凭空消失」。

### 1. 必须走 `MessageSource.executeMessages(msg, true)`

最后一个参数 `true`（init）会触发 `Schema.initShapeFunctions()` + `Designer.painter.renderShape()`。
直接调 `Model.addMulti()` 只改数据、画布不重绘。

### 2. 坐标在视口外会被**静默删除**

`Designer.painter.renderShape` 第一行就是 `if (!Utils.isInCanvasView(e)) return $('#'+e.id).remove(), void ...`。
越界不报错，图元直接消失。

`Utils.canvasViewBox.x === document.getElementById('designer_layout').scrollLeft - 1200`。
桥接层里的 `clampIntoView` 就是处理这个，并且在视口比元素还小时退化为居中。

### 3. 颜色是 RGB 逗号串，不是 hex

```js
fillStyle: { drawType: 'fill', fill: '255,235,235', alpha: 1 }
lineStyle: { lineWidth: 2, lineColor: '255,0,0', lineStyle: 'solid' }
```

写 `#ff0000` 不生效。证据：`Schema.shapeDefaults.lineColor === "33,41,48"`。

### 4. 缺字段的图元会被渲染器跳过

节点必须带 `children: []`、完整的 `attribute` 对象、`path`、`anchors`、`textBlock`。

## 四、DSH 侧的额外坑

### 后台标签页会休眠

`browser_evaluate` 有 **100ms 超时**。页面在后台被休眠后，**无论表达式多简单都超时**（实测连 `1+1` 都可能超时）。

诊断顺序：
1. `1+1` — 连这个都超时 = 休眠，重新激活
2. `typeof window.POBridge` — 超时 = 休眠
3. `Object.keys(Model.define.elements).length` — 前两个过、这个超时 = 图太大

### 写操作超时是常态，不是失败

真机实测（53 节点 / 62 连线的泳道图）：

| 操作 | 表面结果 | 实际结果 |
|---|---|---|
| `createNode` | eval timeout | **已创建**，图元数 115→116 |
| `updateNode` | eval timeout | **已生效** |
| `removeNodes` | 正常返回 | 已删除 |

3 个里 2 个超时但都已生效。**把超时当失败去重试，必然产生重复图元。**

正确做法：显式生成 id → 超时先 `existsExpr(id)` 探测 → 确认不存在才重试。

### JS 模板字符串会吞掉 `\d`

页面片段里写 `/file_id=(\d+)/`，经模板字符串后变成 `/(d+)/` —— 静默失效，不报错。

规矩：**片段内部不允许出现反斜杠**，用 `[0-9]` 代替。`selftest` 有专门的断言守着这条。

## 五、工程实践

### 单一源码 + 可复现构建

桥接层曾经在仓库里有 5 份产物、3 种内容，没有构建脚本 —— 没人能证明哪份是新的。

现在：
```bash
node bridge/build.mjs           # 构建 3 个产物
node bridge/build.mjs --check   # 校验漂移，不一致退出码 1
```

### 测试（全部离线，不需要浏览器）

```bash
cd dsh/skill/dsh-processon-diagram-editor
node test/selftest.mjs   # 36 项：片段可编译 / 转义无损 / 守卫存在 / 自包含 / 书签版本
node test/parity.mjs     # 两个产物行为是否一致

cd wb && node test/selftest.mjs   # 24 项
```

这些测试不是摆设 —— 它们当场抓到过真 bug：
- 反斜杠被模板字符串吞掉（`TAB_IDENT` 的 file_id 正则变成 `(d+)`）
- 路径拼接错误（技能自包含重构后）
- 书签工具跑的是 margin=40 的旧桥接层（与主桥接层不一致）

### 技能必须自包含

装到用户机器时只复制技能目录。`lib/` 和 `test/` 曾经在外面，装过去就丢。
现在 `selftest` 有断言强制这一点。

## 六、走过的弯路（都纠正了）

| 曾经的判断 | 实际情况 |
|---|---|
| 「ProcessOn 没有写入接口」 | 有，`MessageSource.executeMessages` |
| 「书签 = 零安装，C 类同事也能用」 | 错。书签解决的是「**人**执行代码」，不是「**AI** 执行代码」 |
| 「install.bat 的旧目录名已修复」 | 只改了已安装副本和 dist，**源文件没动** |
| 「`processon-diagram-generator` 是悬空引用」 | 它由技能市场提供，只是不在 `~/.dsh/skills` 扫描根下 |
| 「文档已还原到 113 图元」 | 当时还有 3 个测试残留物（115） |

这些错误的共同原因：**只看了一层，没有交叉验证**。记录下来提醒后来者。

## 七、没做的事（有意的）

- **文字颜色改不动**：元素级 `fontColor` 会写进模型，但文字层仍渲染成深灰。红标靠边框/填充/连线。
- **DSH 版不做落库校验**：没有可靠手段确认是否存进服务端，所以文档里明确写「不许声称已保存」。
- **不做从零新建整图**：那是 `processon-diagram-generator` 的活。

---

## 八、已知风险

1. **非官方接口**。`Model` / `MessageSource` / `Designer` 没有任何稳定性承诺，ProcessOn 前端发版可能失效。
   失效时桥接层会明确报 `NO_BRIDGE` / `NO_MODEL`，不会假装成功。
2. **改动实时广播**。走协同通道，动手前最好在群里说一声。
3. **URL 票据等同编辑权限**。DSH/WorkBuddy 方案涉及复制编辑页 URL，别外传。
