# DSH 方案 vs WorkBuddy 方案 —— 逐项对比

> 两套都能改图，能力核心相同（同一份 `bridge/pobridge.js`）。
> 真正的差别不在「能不能改」，在**谁去执行**、**你要付什么代价**、**什么场景会卡住**。
>
> 本文所有数据来自本机实测（Windows 11 / Edge 156 / Node 24.12 / 2026-11-04），
> 未实测的地方会明确标注「未验证」。

---

## 一、一张表看懂

| 维度 | DSH 方案 | WorkBuddy 方案 |
|---|---|---|
| **执行者** | DSH 通过浏览器扩展驱动**你正开着的标签页** | Playwright 自起一个 **headless Chromium** |
| **进入编辑态靠什么** | 你已登录的会话（Cookie） | URL 里的 `encrypted_session` 票据 |
| **要装的东西** | DSH 本体 + 扩展(165 KB) + 技能(89 KB) | Node 20+ + playwright-core(14 MB) + Chromium(≈300 MB) + 技能(104 KB) |
| **单次读图耗时** | **6–30 ms**（热标签页，实测 12/12 成功） | **2.9–3.9 s**（冷启浏览器，实测 smoke 3880 ms） |
| **一次写入耗时** | 未知（写操作常超出 100 ms 预算，见 §3.1） | ~7 s（含 Ctrl+S），带 verify 约 12 s |
| **会打断你吗** | **会**。必须激活标签页 + 等 2.5 s | **不会**。全程后台 |
| **能无人值守 / 定时吗** | 不能 | **能**（headless） |
| **能确认真的落库吗** | **不能** | **能**（`pocli verify` 另起干净浏览器比对） |
| **自动保存** | 不做（刻意设计） | 默认 Ctrl+S |
| **多图 / kdocs 内嵌** | **处理得了**（7 处专门逻辑） | **处理不了**（只认 URL 里的 `file_id`） |
| **出错时的报错质量** | 依赖 AI 自己判断 | 结构化退出码 0/2/3/4/5/6/7 |
| **可测试性** | 46 项离线断言 + 33 项泳道池行数验证；**无集成测试** | 24 项离线断言 + **实际集成 smoke** |
| **升级路径** | 覆盖安装技能目录 | `sync-skill.mjs` + SYNC.json 哈希校验 |

## 二、DSH 方案的真正优势

### 2.1 你有眼睛，AI 才有眼睛

这是最被低估的一条。DSH 方案改的是**你眼前那个标签页**：

- 改完你**立刻看见**，不用刷新、不用等协同同步
- 位置不对你**当场喊停**，AI 下一句就能改
- 你和 AI 看的是同一个画面，讨论「第三泳道那个判断框」不会指错

WorkBuddy 方案改完之后，你要么去 ProcessOn 刷新，要么跑 `shot` 截图再看。
多了一步「取证」，协作节奏就断了一拍。

### 2.2 读图快一个数量级

实测对比（同一张 52 节点 / 61 连线的泳道图）：

| 动作 | DSH | WorkBuddy |
|---|---|---|
| 冷启动到能读 | 激活 168 ms + 等 2.6 s = **2.8 s** | **2.9 s**（`open` 阶段） |
| 第二次读 | **6–30 ms** | 每次都要重启进程，≈3–5 s |

原因很简单：DSH 复用一个已经暖着的标签页，WorkBuddy 每次都是新进程 + 新页面。

**推论**：需要来回读很多次的任务（对账、逐泳道核对、批量改文案），DSH 快得多。

### 2.3 不用装 Chromium

WorkBuddy 那 300 MB 的 Chromium 是硬成本。DSH 侧只多一个 165 KB 的扩展。

对**非技术同事**来说这是决定性的：装扩展是「打开 edge://extensions 点五下」，
装 Node + 等 Chromium 下载是另一回事。

### 2.4 多图场景是它的主场

用户桌上常年开着七八个 kdocs 标签，其中若干内嵌 ProcessOn 图。
DSH 技能里有 **7 处专门处理 kdocs** 的逻辑：读 `#dotviewIframe.src`、新开标签页、
跨域隔离、逐个识别 `file_id`。

WorkBuddy 侧**完全没有**这部分（`grep kdocs` 零命中）—— 它只认 URL 里带 `file_id` 的直连地址。
遇到 kdocs 内嵌图，用户得自己先把 iframe 的 src 抠出来。

## 三、DSH 方案的真正劣势

### 3.1 `browser_evaluate` 只有 100 ms —— 这是天花板的由来

**实测把边界卡出来了**（同步忙等循环）：

| 页面侧执行时长 | 结果 |
|---|---|
| 30 ms | OK（往返 41 ms） |
| 60 ms | OK（往返 69 ms） |
| 90 ms | OK（往返 100 ms） |
| **120 ms** | **ERR eval timeout after 100ms** |
| 160 ms | ERR |

而且 **async 一律不行**：

```
(async function(){ await new Promise(r=>setTimeout(r,200)); ... })()
→ eval timeout after 100ms
```

`browser_wait({fn})` **不是**逃生口 —— 实测传 async 谓词 8 ms 就返回了，
Promise 对象本身是真值，等于立刻通过。

**为什么这很痛**：改图要调 `MessageSource.executeMessages(msg, true)`，
它会触发 `Designer.painter.renderShape()` 重绘整张 SVG。图一大就必然超 100 ms。
于是出现了一个反直觉的常态：

> **写操作超时是正常现象，不是失败。**

技能里记录了真机数据：3 次写入里 **2 次超时，但两次都已生效**。
所以 DSH 侧必须带着「超时 → 先探测 `existsExpr(id)` → 确认不存在才重试」这套仪式走。
漏一步就多出一个重复图元。

WorkBuddy 侧没有这个约束：`page.evaluate` 默认等 30 s，写就是写。

### 3.2 必须打扰你（这一点无法绕开）

后台标签页会被浏览器休眠。休眠后**连 `1+1` 都超时**。
所以每次动手前必须：

1. `browser_tabs({action:'activate', tabId})` —— 你的屏幕会被切走
2. 等 **2.5 s** 让它醒过来
3. 才能干活

我实测过：即便激活后等了 2.5 s，**第一次 eval 仍可能超时**，第二次才稳定。
多图排查时这个切换会反复发生。

### 3.3 没有落库校验 —— 不许说「已保存」

DSH 侧**无法确认改动是否真的进了服务端**。技能里明确写：

> `不要声称「已保存」—— 你无法验证。`

WorkBuddy 侧有 `pocli verify`：另起一个干净的 headless 浏览器，
不带任何你的登录态，读服务端副本，比对节点数。这是硬证据。

**代价**：DSH 用户按 Ctrl+S 之后，只能靠「刷新一下看看还在不在」来确认。

### 3.4 「能跑」多依赖 AI 现场判断

DSH 技能是一份 **256 行 Markdown 说明书**。流程正确性靠 AI 读懂并遵守。
WorkBuddy 是一个 **508 行 CLI**，流程正确性靠代码 + 退出码。

| | DSH | WorkBuddy |
|---|---|---|
| 流程约束在哪 | SKILL.md 的文字 | 代码里的 `applyOnce` / `ensurePointVisible` |
| 违反约束会怎样 | 无人阻止，AI 可能漏步骤 | 参数非法直接退出码 2 |
| 换个模型还稳吗 | 不保证 | 保证 |

这不是说 DSH 不可靠 —— 是**责任主体的差别**。

## 四、WorkBuddy 方案的真正优势

1. **不碰你的浏览器**。你继续干你的活，AI 在后台改图。
2. **可以无人值守**。挂个定时任务，每天自动读图、生成报告、检查流程合规性。
3. **落库可验证**。`verify` 是真·服务端比对。
4. **确定性高**。20887 字节的 CLI，13 个子命令，每条都有退出码。
5. **有真集成测试**。`test/smoke.mjs` 真开页面读数，3.88 s 跑完：
   `52 节点 / 61 连线 / 页面 4027×3862 / 池底 2720` —— 与本机保存的原始图数据完全一致。
   （原始数据 `data/processon-raw.json` 含具体业务内容，不随仓库分发。）
6. **技能自包含且有溯源**。`sync-skill.mjs` 把运行时同步进技能目录，
   `SYNC.json` 记录来源 commit + 每个文件哈希，`--check` 能抓漂移。

## 五、WorkBuddy 方案的实际成本

### 5.1 装起来比想象中重

`npm i` 只装 `playwright-core`（14 MB，不下载浏览器）——但**浏览器是必须的**。
本机 `ms-playwright` 缓存已经 **1.6 GB**（两个版本 chromium-1208 / 1248）。

对没装过 Playwright 的同事，实际步骤是：
装 Node → `npm i` → `npx playwright install chromium`（下载 100–300 MB）→ 才跑得起来。

安装指南里写「不会下载浏览器——本机已有 Playwright 缓存时直接复用」，
这句对**已有缓存的人**成立，对**新同事**是个坑。

### 5.2 票据会过期

`encrypted_session` 从 URL 来。过期就得回浏览器复制新 URL 再 `set-url`。
用户得知道「为什么昨天能跑今天不能」。

### 5.3 票据落盘 = 编辑权限落盘

`wb/.pocli-state.json` 存的是完整编辑页 URL，**等同于这张图的编辑权限**。

代码写了 `mode: 0o600`，但本机实测落盘仍是 **644**（在 NTFS 上用同一段代码写测试文件，
`stat` 结果一致为 644）。原因：Node 的 `mode` 只在 POSIX 上生效，
Windows 走继承 ACL。**这行代码在 Windows 上不产生保护效果。**

原来的 README 写「权限 600」，那是假的安心感 —— 已删掉该表述，
并在这个 writeFileSync 上方加了注释说明实际情况。

真正的保护只有一条：**别外传 `.pocli-state.json`**。另外它已在 `.gitignore` 里。

## 六、怎么选 —— 决策树

```
你用 DSH 吗？
├─ 是 → DSH 方案（扩展已经装了，边际成本接近零）
│       除非你需要：无人值守 / 落库校验 → 那就再装 WorkBuddy 侧
└─ 否 → 你用 WorkBuddy 吗？
         ├─ 是 → WorkBuddy 方案
         └─ 都不是 → 只想要个能点的书签 → 03-通用工具
```

**需要同时装两套吗？** 一般不需要 —— 它们改的是同一份文档、同一份数据。
但下面两种情况值得装两套：

- 日常改图要**边看边改**（用 DSH），偶尔要**跑脚本批量核对**（用 WorkBuddy）
- 要交叉验证：DSH 改完，用 WorkBuddy 的 `verify` 确认真的落库了

**这个交叉验证是真的有用的** —— 它补上了 DSH 唯一的结构性缺口。

## 七、如果只能改一处，改哪里

按性价比排序：

| # | 改动 | 收益 | 成本 |
|---|---|---|---|
| 1 | 把 WorkBuddy 的 `verify` 思路搬进 DSH | 补上「不知道存没存进去」这个缺口 | 中（要起第二个浏览器，DSH 侧没这能力 → 实际只能引导用户刷新） |
| ~~2~~ | ~~修 `.pocli-state.json` 的权限声明~~ | ✅ **本次已改**：删掉 README 里的「权限 600」，pocli 里加了注释说明 Windows 上不生效 | 已做 |
| 3 | WorkBuddy 加 kdocs 支持 | 补上 7 处逻辑的缺口 | 中高 |
| 4 | DSH 技能加集成 smoke 测试 | 现在只有离线断言，页面片段是否真能跑没验证 | 中 |

> 第 4 条值得单独说：DSH 侧 46 项断言全是**离线字符串检查**（片段能编译、没反斜杠、守卫存在）。
> 它证明不了「这段 JS 丢进 ProcessOn 真的能跑」。
> WorkBuddy 侧的 smoke 测试证明得了。这是 DSH 侧当前的测试盲区。

## 八、共同的软肋

两套都建立在这三个全局对象上：

```
window.Model          // 文档模型
window.MessageSource  // 事务管道
window.Designer       // 渲染器
```

**没有任何稳定性承诺。** ProcessOn 前端发一次版就可能全废。
所以两边都写了「失效时如实报错，不假装成功」——这是底线，不是可选项。

其它共同限制：

- **文字颜色改不动**。元素级 `fontColor` 写进去了，文字层仍渲染成深灰。
  红标只能在边框/填充/连线上体现。
- **改动实时广播**。走协同通道，同事那边立刻看见。动手前在群里说一声。
- **别拿没备份的重要图做实验**。
